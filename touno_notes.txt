Para tu arquitectura (web + móvil nativa + backend propio) no hay un solo catálogo: te tocan tres superficies distintas, y OWASP tiene un
  catálogo verificable para cada una.

  Los que realmente se "cumplen" (requisitos testeables)

  1. OWASP ASVS 5.0 — para el frontend web y el backend.
  Es el estándar de verificación: ~350 requisitos en 17 capítulos, con 3 niveles de aseguramiento. Es el único de la lista que se puede auditar
  requisito por requisito.
  - Nivel 1: mínimo, verificable sin acceso al código.
  - Nivel 2: el objetivo realista para una app con usuarios y datos personales. Empieza aquí.
  - Nivel 3: apps críticas (salud, finanzas, vidas humanas).
  
  Capítulos que te van a pegar más fuerte con tu diseño: autenticación, gestión de sesión, autorización, tokens auto-contenidos (JWT),
  OAuth/OIDC, comunicación segura y API/web services. Los capítulos de tokens y OAuth son nuevos en 5.0 justamente por arquitecturas como la
  tuya.

  2. OWASP MASVS 2.x — para la app móvil nativa, y solo para ella.
  El equivalente de ASVS en móvil, en 8 grupos: STORAGE, CRYPTO, AUTH, NETWORK, PLATFORM, CODE, RESILIENCE, PRIVACY. Va acompañado del MASTG
  (guía de testing, el "cómo se prueba cada control") y el MAS Checklist, que es el Excel que usarías en una auditoría.

  Ojo con un detalle que se pasa por alto: si la móvil es nativa, el cliente es hostil por definición — está en un dispositivo que el usuario
  controla. Nada de secretos embebidos en el binario, nada de validación de negocio solo en el cliente. Eso es MASVS-STORAGE y MASVS-CODE.

  Los que son listas de concientización (no se "certifican", pero se usan)

  3. OWASP API Security Top 10 (ed. 2023) — este es el que más te aplica y el que la gente olvida.
  Tu backend sirve a dos clientes distintos; eso multiplica los riesgos de autorización. Los tres primeros son literalmente tu escenario:
  - API1 – BOLA (Broken Object Level Authorization): /pedidos/123 devolviendo el pedido de otro usuario. La falla nº1 en APIs, siempre.
  - API3 – Broken Object Property Level Authorization: mass assignment y exposición de campos de más (típico cuando devuelves la entidad completa
    "porque el frontend la filtra").
  - API5 – Broken Function Level Authorization: el endpoint de admin accesible desde la app móvil.
  - API9 – Improper Inventory Management: te va a morder cuando tengas /api/v1 para web y /api/v2 para móvil y la v1 quede viva sin
    mantenimiento.

  4. OWASP Top 10:2025 — la edición vigente (anunciada nov-2025, final en enero 2026). Reemplaza a la de 2021.
  Cambios que te importan: A01 Broken Access Control sigue nº1 y ahora absorbió SSRF; A02 Security Misconfiguration subió al 2º puesto; y entran
  dos categorías nuevas: A03 Software Supply Chain Failures y A10 Mishandling of Exceptional Conditions.

  5. OWASP Mobile Top 10 (2024) — la versión de concientización de MASVS. M1 Improper Credential Usage, M4 Insufficient Input/Output Validation,
  M9 Insecure Data Storage.

  Lo que yo priorizaría, en orden
  
  Como estás en fase de implementación y no de auditoría, el orden importa más que la lista completa:

  1. OWASP Proactive Controls primero. Está escrito para desarrolladores, no para auditores — es el puente entre "no sé por dónde empezar" y
     ASVS.
  2. API Security Top 10 como checklist mental en cada endpoint que escribas. Es donde vive el 80% de tu riesgo real.
  3. ASVS 5.0 Nivel 2 como meta formal del backend + web.
  4. MASVS cuando la app móvil pase de prototipo a algo que guarde sesión o datos.
  5. Las Cheat Sheets de OWASP como referencia puntual (JWT, session management, autenticación) — son la respuesta concreta a "sí, pero ¿cómo lo
     implemento en Spring/ASP.NET?".

  Una advertencia sobre alcance: ASVS y MASVS no se solapan, se complementan, pero tampoco cubren tu backend dos veces. El error común es
  intentar aplicar MASVS al servidor o ASVS al binario móvil. Cada catálogo tiene su superficie: ASVS = servidor y navegador, MASVS = binario y
  dispositivo, API Top 10 = el contrato entre ambos.

  Si me dices el stack concreto del backend (Java/Spring o C#/.NET, según tu perfil), puedo aterrizar los requisitos de ASVS L2 a controles y
  librerías específicas en lugar de dejarlo en el nivel de estándar.

❯ cuáles son los métodos de cifrado más usados como estándar para proteger información sensible?                                                 

● Buena pregunta para enganchar con lo anterior — esto es exactamente A04:2025 Cryptographic Failures, ASVS V11 (Cryptography) y MASVS-CRYPTO.
  
  Antes de la lista, la distinción que más se equivoca la gente: "proteger información sensible" son tres problemas distintos con tres soluciones
  distintas. Elegir el algoritmo correcto para el problema equivocado es peor que no cifrar.

  ---

  1. Cifrado simétrico — datos en reposo y payloads

  Es lo que usas para cifrar datos que necesitas recuperar en claro después.

  ┌─────────────────────────┬───────────────────────────────────────────────────────────────────────────┬──────────────────────────────────┐
  │        Algoritmo        │                                    Uso                                    │              Estado              │
  ├─────────────────────────┼───────────────────────────────────────────────────────────────────────────┼──────────────────────────────────┤
  │ AES-256-GCM             │ El estándar de facto. Cifra y autentica a la vez (AEAD)                   │ ✅ Primera opción                │
  ├─────────────────────────┼───────────────────────────────────────────────────────────────────────────┼──────────────────────────────────┤
  │ ChaCha20-Poly1305       │ Alternativa a AES; más rápido en móviles sin aceleración AES por hardware │ ✅ Ideal para tu app móvil       │
  ├─────────────────────────┼───────────────────────────────────────────────────────────────────────────┼──────────────────────────────────┤
  │ AES-256-CBC             │ Solo cifra, no autentica                                                  │ ⚠ Requiere HMAC aparte; evítalo │
  ├─────────────────────────┼───────────────────────────────────────────────────────────────────────────┼──────────────────────────────────┤
  │ AES-ECB, DES, 3DES, RC4 │ —                                                                         │ ❌ Rotos o inseguros             │
  └─────────────────────────┴───────────────────────────────────────────────────────────────────────────┴──────────────────────────────────┘

  La clave está en el modo, no en el tamaño. "Uso AES-256" no dice nada: AES-256-ECB filtra patrones del texto plano (el famoso pingüino de Tux
  que sigue viéndose después de cifrar). Siempre AEAD: GCM o Poly1305. Y nunca reutilices un nonce/IV con la misma clave — en GCM eso no degrada
  la seguridad, la destruye por completo.

  2. Cifrado asimétrico — intercambio de claves y firmas

  ┌──────────────────────┬──────────────────────────────────────────────────────────────────────┐
  │      Algoritmo       │                                 Uso                                  │
  ├──────────────────────┼──────────────────────────────────────────────────────────────────────┤
  │ X25519 / ECDH        │ Intercambio de claves (lo que hace TLS por debajo)                   │
  ├──────────────────────┼──────────────────────────────────────────────────────────────────────┤
  │ Ed25519              │ Firma digital. Rápido, curvas modernas, difícil de implementar mal   │
  ├──────────────────────┼──────────────────────────────────────────────────────────────────────┤
  │ ECDSA P-256          │ Firma. Muy soportado (JWT ES256, certificados)                       │
  ├──────────────────────┼──────────────────────────────────────────────────────────────────────┤
  │ RSA-2048/4096 + OAEP │ Legacy pero omnipresente. Si cifras con RSA, OAEP, nunca PKCS#1 v1.5 │
  └──────────────────────┴──────────────────────────────────────────────────────────────────────┘

  En la práctica casi nunca cifras datos directamente con asimétrico — es lento y limitado en tamaño. Se usa cifrado sobre: generas una clave AES
  aleatoria, cifras los datos con ella, y cifras esa clave con RSA/ECDH. Es lo que hace todo KMS por dentro.

  3. Contraseñas — esto NO es cifrado

  Las contraseñas no se cifran. Se hashean con una función deliberadamente lenta. Cifrar implica poder descifrar, y tú nunca debes poder
  recuperar la contraseña de un usuario.

  ┌────────────────────────────────┬───────────────────────────────────────────────────────────────────────────────┐
  │           Algoritmo            │                                 Recomendación                                 │
  ├────────────────────────────────┼───────────────────────────────────────────────────────────────────────────────┤                 
  │ Argon2id                       │ ✅ El estándar actual (ganador del Password Hashing Competition)              │
  ├────────────────────────────────┼───────────────────────────────────────────────────────────────────────────────┤
  │ scrypt                         │ ✅ Buena alternativa                                                          │
  ├────────────────────────────────┼───────────────────────────────────────────────────────────────────────────────┤
  │ bcrypt                         │ ✅ Aceptable, muy maduro. Ojo: trunca a 72 bytes                              │
  ├────────────────────────────────┼───────────────────────────────────────────────────────────────────────────────┤
  │ PBKDF2-HMAC-SHA256             │ ⚠ Aceptable solo si necesitas certificación FIPS. Mínimo 600.000 iteraciones │
  ├────────────────────────────────┼───────────────────────────────────────────────────────────────────────────────┤
  │ MD5, SHA-1, SHA-256 "con salt" │ ❌ Son rápidos. Una GPU prueba miles de millones por segundo                  │
  └────────────────────────────────┴───────────────────────────────────────────────────────────────────────────────┘

  4. Integridad y hashing general

  - SHA-256 / SHA-512 — hashing de propósito general (checksums, huellas de certificados).
  - SHA-3 / BLAKE3 — alternativas modernas.
  - HMAC-SHA256 — autenticación de mensajes con clave compartida (firmas de webhooks, tokens HS256).
  - ❌ MD5 y SHA-1 están rotos para cualquier uso de seguridad. Existen colisiones prácticas desde hace años.

  5. En tránsito

  TLS 1.3, y punto. Deshabilita TLS 1.0/1.1 y preferentemente 1.2. En tu app móvil, además: certificate pinning (MASVS-NETWORK) — sin él,
  cualquiera con un proxy y un certificado instalado lee todo tu tráfico API.

  6. Post-cuántico — ya no es teoría

  NIST estandarizó en agosto de 2024:

  - ML-KEM (ex-Kyber, FIPS 203) — intercambio de claves
  - ML-DSA (ex-Dilithium, FIPS 204) — firmas
  - SLH-DSA (ex-SPHINCS+, FIPS 205) — firmas basadas en hash

  Los navegadores y CDNs principales ya negocian híbrido X25519 + ML-KEM en TLS por defecto. Para tu app no necesitas hacer nada activamente hoy,
  pero sí importa si guardas datos que deban seguir confidenciales más de ~10 años: el ataque "harvest now, decrypt later" consiste en capturar
  tráfico cifrado hoy para descifrarlo cuando haya un computador cuántico.

  La regla que más te va a servir: no implementes primitivas criptográficas. Usa capas de alto nivel que eligen los parámetros por ti:

  - Java → Google Tink (https://developers.google.com/tink), o javax.crypto con AES/GCM/NoPadding; Spring Security para Argon2/bcrypt.
  - .NET → System.Security.Cryptography.AesGcm, y ASP.NET Core Data Protection API para el caso general (gestiona rotación de claves sola).
  - Multiplataforma → libsodium.

  Y el punto que hunde más implementaciones que el algoritmo: la gestión de claves. Un AES-256-GCM impecable con la clave hardcodeada en el
  repositorio o en application.properties no protege nada. Claves en KMS (AWS KMS, Azure Key Vault, GCP KMS) o Vault, con rotación definida,
  fuera del código y fuera del control de versiones.

  Si me dices si el backend es Spring o .NET, te aterrizo esto a código concreto con la configuración correcta.
